# Spec 003 上游升级漂移同步（能力发现升级 + 漂移提醒 + 官方自动归组）

## 状态

- 文档性质：需求规格
- 对应版本：v0.1.4
- 状态：**已实现（v0.1.4，2026-09-30）**
  - 需求确认方式：用户 2026-09-30 原话（"dsh 升级后…要同步更新到其他分组里面，避免我不知道"）
    即 R1–R3 的需求确认；Q1–Q3 澄清问题用户未回答，按推荐选项执行（R4 浏览器重启用与

- 维护者：AI + 用户
- 触发事件：2026-09-29 DSH 0.1.x → 0.2.0-rc.x 升级后，右侧栏（hub 分类页）不再出现内置浏览器等
  原生能力，用户无法察觉"上游升级引入/移除了什么"。

## 0. 背景与诊断结论（证据链）

### 现象

- 用户观察：DSH 升级后，原生右侧栏有浏览器等能力，但（hub 接管的）右侧栏起始页里看不到。

### 诊断结论（2026-09-30 实测）

1. **浏览器消失的直接原因是上游，不是 hub 的 bug**：
   - 上游 0.2.0 的 web 组合里 `ui-sidebar-browser` 被**默认禁用**：
     `packages/bundle/web-app/cordis.patch.yml`：
     `disabled: !!js "ctx.get('profileContext')?.name !== 'desktop'"`（注释：Web profiles opt in；
     Desktop 保留沙箱浏览器 tab）。上游 e2e `web-default-isolation.expected.e2e.ts` 明确断言
     默认 web 交付图**不含** `dsh-client-ui-sidebar-browser`。
   - 实测本机会话（3082，DSH 0.2.0-rc.1）的 `__DSH_BOOT__` 启动图（82 行）中**无** browser 行；
     插件未加载 ⇒ `sidebarRightTabs` 注册表里根本没有 `browser` 类型 ⇒ 原生引导页与 hub 分类页
     都不可能显示它（`openTab('browser')` 会抛错）。0.1.x 时代 web 侧内置浏览器，升级后消失。
   - 恢复途径（上游支持的 profile 层覆盖，参照上游测试 overlay `sidebar-browser.overlay.yml`）：
     在 `~/.dsh-dev/profiles/web/cordis.patch.yml` 追加
     `- id: ui-sidebar-browser` / `disabled: false`，重启后 web 侧启用（web 为 iframe 形态浏览器；
     桌面端为一等公民）。
2. **hub 设计缺陷 A —— 发现面过窄**：hub 只读 `sidebarRightTabs.guide()`（只覆盖"声明了引导胶囊
   的类型"）。注册表还有公开 API `entries()`（全部在编类型，含无引导胶囊者）未利用。上游新引入的
   原生能力若没有 guide 条目，hub 永远看不见。
3. **hub 设计缺陷 B —— 无漂移感知（本次事故的主因）**：hub 对注册表没有"上次看到过什么"的记忆。
   上游**移除/停用**一个能力（如 0.2.0 的浏览器）、或**新增**一个能力时，分类页静默变化，用户
   完全无感知——正与用户诉求"避免我不知道"相反。
4. **hub 设计缺陷 C —— 官方性硬编码**：`OFFICIAL_KINDS` / `DEFAULT_ENTRY_RULES` 是 0.1.x 时点的
   手工快照（files/text/guide/terminal/browser）。上游新增原生 kind 时只能落「其他」，无法自动进「官方」。

### 非目标（本 spec 不做）

- 不修改上游任何源码/组合；不改 `deepseek-harness`。
- 不接管浏览器本身（web 侧 iframe 形态仍由上游 `ui-sidebar-browser` 提供；本插件只做入口编排）。
- 不做"跨插件能力注册表"或 host 侧能力清单服务；不引入新的网络端点。
- 不改变现有分组/拖拽/设置卡片交互；不改变 settings 深合并语义。

## 1. 目标（一句话）

**上游 DSH 每升级一次，右侧栏分类页自动回答"多了什么、少了什么"：新原生能力自动归入「官方」组
（第三方新能力落「其他」并带"新"标记），被上游移除/停用的能力以提醒条明示，用户永远不靠猜。**

## 2. 需求（用户可感知行为）

### R1 全量能力发现（修缺陷 A）

- 分类页条目 = 注册表**全部在编类型**（`registry.entries()`）∪ 引导条目（`guide()`），按 kind 去重。
- 无引导胶囊的类型也要出现在分类页（标题取 `definition.title('')`），点按仍走 `openTab(kind)`。
- 效果：上游新加任何右侧栏类型（哪怕未声明引导胶囊）都会出现，不再"只认引导胶囊"。

### R2 升级漂移提醒（修缺陷 B；用户核心诉求）

- host 在 settings 命名空间 `dsh-sidebar-hub` 持久化「能力快照」（kind → {title, 官方性, 首次出现/消失时点}）。
- 每次刷新注册表后与快照比对：
  - **新增 kind**：条目带「新」角标；
  - **消失 kind**（快照有、注册表无）：分类页顶部提醒条列出（如"浏览器 自 0.2.0 起未再注册，
    可能上游已停用/改为仅桌面端，可检查 profile 补丁或上游版本"）。
- 提醒条可「知道了」关闭（按差异签名记忆，同类差异不重复弹）；关闭即把当前注册表写回快照。
- 首次运行（无快照）静默初始化，不提醒。

### R3 新能力自动归组（修缺陷 C）

- 注册表条目带提供方身份（`definition.id` / guide box 的 `providerId`）：
  `@deepseek-ai/*` = 官方原生，其余 = 第三方/自研。
- **用户未配置归属**的新 kind：官方原生 → 自动进「官方」组；其余 → 「其他」组（均带「新」角标）。
- 用户拖拽/设置页的显式归属**永远优先**于自动规则；「官方」角标按提供方身份显示，不再靠硬编码名单。
- `OFFICIAL_KINDS` 常量保留仅作设置卡片的兼容兜底，不再是唯一官方性来源。

### R4 浏览器（web 侧）恢复

- 交付 profile 层补丁（追加到 `~/.dsh-dev/profiles/web/cordis.patch.yml`）：
  `- id: ui-sidebar-browser` / `disabled: false`（上游 profile patch 机制的公开用法，与上游
  `sidebar-browser.overlay.yml` 同一形态）。重启后 web 侧内置浏览器回归，自动被 R1/R3 收录进「官方」组。
  （注：web 为 iframe 形态；上游 0.2.0 默认只对 desktop 启用，本机启用属于用户主动 opt-in。）

## 3. 非目标与边界

- 上游**禁用**的类型（如 web 侧未启用前的 browser）注册表里根本不存在：漂移提醒只能说"少了 X"，
  不能让它凭空出现——这是上游组合的权限，profile 补丁（R4）是用户的官方恢复途径。
- 不尝试从 DSH 版本号反推能力清单（无版本→能力映射的公开契约）。
- 「知道了」之后同类差异不重复提醒；下一次**新的**差异仍会提醒。

## 4. 验收标准（用户可感知，真实实例）

1. 测试实例（3084/3085）加载新版本后：分类页出现**全部**在编右侧栏类型，含无引导胶囊者；
   浏览器启用补丁后出现「浏览器」（官方角标，官方组）。
2. 人为模拟漂移（测试实例先启后停一个测试插件类型）：分类页出现"新增/移除"提醒条，含具体 kind；
   点「知道了」后消失且不再重复；重启后快照生效。
3. 3082 实例（用户批准后重装 + 重启 + 应用浏览器补丁）：右侧栏恢复浏览器入口；官方组含
   文件/终端/浏览器；分类页无静默缺失。
4. `pnpm check` 全绿；双端产物门禁通过；设置卡片新增行可维护「新」条目的归属。
5. 文档同步：`docs/index.md`、`REQUIREMENTS.md`、本 spec、`TROUBLESHOOTING.md`（浏览器消失事故）。

## 5. 风险与回滚

- 风险 1：`entries()` 返回的内部 kind（如 guide/text 预览器）混入分类页——沿用现有默认隐藏规则
  （guide/text 隐藏），新增内部 kind 落「其他」，用户可拖走或隐藏。
- 风险 2：web 侧启用 iframe 浏览器为上游默认关闭项（web-default-isolation 是上游有意设计）——
  仅在**本机 profile** 启用，不改上游；如上游后续改变该包契约，补丁条目仍走公开 loader 层。
- 回滚：tgz 降回 0.1.3 + 删除 profile 补丁行 + 重启；settings 快照键为新增键，旧版忽略不碍事。
